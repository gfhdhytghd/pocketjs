One application model / Two execution classes

Keep the app semantics.
Change the machinery underneath.

PocketJS starts with what the app means and what the target can do. The browser, DOM, runtime CSS—and even the JavaScript engine—are implementation choices, not requirements.

01 Pocket Guest

Keep JavaScript dynamic. For machines that can afford a tiny embedded engine.
Vue / Solid / TS → QuickJS guest → Native core → Host
  • Portable guest bundle and hot-swappable app policy
  • Native retained UI, layout, text and rendering
  • Runtime admission against explicit capabilities
PSP PS Vita PocketBook macOS widget Nokia E7 · experimental

02 Pocket Vapor

Compile the runtime away. For machines where even an interpreter is too expensive.
Vue model → AOT compiler → Dirty-bit native code → ROM
  • A strict Vue Vapor TypeScript and JSX subset
  • No JavaScript engine, garbage collector or allocator
  • Compile-time admission against board profiles
GBA Game Boy NES ESP32 MeowBit

Same authoring instincts. Different artifacts. No single runtime pretending every machine is the same.

Familiar code / Native machinery

One guest app.
Four very different hosts.

The source stays portable where the guest fits. A target profile resolves the viewport, capabilities, raster density and native backend before the app boots.

counter.tsx Vue Vapor / TypeScript 
import { ref } from "vue";
import { Text, View }
  from "@pocketjs/framework/vue-vapor/components";

export default function Counter() {
  const count = ref(0);

  return (
    <View class="flex-col gap-4 p-6">
      <Text class="text-2xl font-bold">
        Count: {count.value}
      </Text>
      <View focusable onPress={() => count.value++}>
        <Text>Press to increment</Text>
      </View>
    </View>
  );
}
